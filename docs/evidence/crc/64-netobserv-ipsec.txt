## 1. How the feature works (netobserv-ebpf-agent source, main branch, bpf/ipsec.h; pkg/decode/flows)
  RETRACTED for the agent that runs here (section 7): the wire-flow rewrite described below is upstream's
  NETOBSERV-2343 (PR #1010, merged 2026-07-30), after the v1.12.0 tag (2026-07-20); the 1.12.3 agent behaves as
  v1.12.0's code does. What follows describes main only.
  kprobe + kretprobe on xfrm_output (egress) and xfrm_input (ingress). The result is stored on the WIRE flow: the
  flow id is rewritten to ESP, or kept as UDP 4500 under NAT-T (ipsec_to_wire_flow_id), so the status lands on the
  node<->NAS ESP/NAT-T flow, not on the inner NFS TCP/2049 flow. Flow fields: IPSecStatus "success" (kernel return
  0) or "error" (IPSecRetCode = the kernel's return code). Built-in metrics node/namespace/workload_ipsec_flows_total
  count flows that have IPSecStatus, labelled by it. A built-in health rule IPsecErrors needs
  node_to_node_ingress_flows_total (warning at apply time).
  Consequence to test: encryption happens before the packet reaches the TC hook where flows are captured, so a TCP
  flow to the NAS's port 2049 seen on egress would be NFS that left the node unencrypted.

## Findings
  1. The IPSec feature marks the node-to-NAS tunnel (External mode, libreswan, NAT-T): 30 flows with
     IPSecStatus="success" on a node whose only IPsec is that tunnel. By address (section 7): the marks do not land
     on the NAS's flows; the plain flows to the NAS show the encryption instead.
  2. Its cost is small in itself: agent 13m / 56Mi, processor 42m / 54Mi at sampling 1 on this node.
  3. The node could not carry the test, and the cause is NOT established. It was at 91% memory before the install;
     within minutes it was reclaiming memory (kswapd0 100%, no swap), the API server slowed (an API call up to
     4.87 s), and operators with leader leases (NetObserv's, Kyverno's) restarted. But another workload was being
     installed on the same node at the same time (section 6), and the load rose again to 80 at 03:31 with NetObserv
     gone. NetObserv's own pods used about 57m and 115Mi. What is established: this node has no memory headroom.
  4. consolePlugin.enable: false does not keep the operator from adding its static plugin to the console's
     configuration (1.12.3): on a cluster where that matters, remove or check it after install.

## Findings of the rerun (section 7)
  5. On a cluster with Dynatrace full stack, NetObserv's agent does not start until NetObserv's namespaces are left
     out of the injection: a DynaKube namespaceSelector is the documented way. Any cluster that runs both needs it.
  6. In 1.12.3, IPSecStatus cannot say whether the NAS's traffic was encrypted on this tunnel (External libreswan,
     NAT-T): the marks are stored under keys that match no flow (7c). The flows themselves can: egress to the NAS
     carries only UDP 4500 (or ESP without NAT-T), and a TCP flow to port 2049 on egress would be cleartext.
  7. On ingress, decrypted NFS appears as TCP from port 2049; it is not cleartext on the wire (7b, the NAS capture).
  8. The four pods used 10m CPU and 227 MiB together at sampling 1 (7e), and the node's load did not change; the
     agent adds TC hooks on every interface and four probes on xfrm.
